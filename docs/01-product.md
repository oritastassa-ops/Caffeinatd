# Caffeinatd — Product Definition (Phase 1)

## Vision

A personal AI secretary for one primary user (with a second account for her partner). It manages
calendar, tasks, fitness, nutrition, and daily planning through natural language, and it is
**proactive**: every morning it produces a plan without being asked. It is not a chatbot with
plugins — the chat surface is a *command bar*, and the product is the structured life-data it
maintains.

## Who it's for

- Primary: one person, non-technical, uses it daily from phone + laptop browser.
- Admin: the builder (you), who deploys it and holds the API keys.
- Explicitly **not** multi-tenant SaaS. Two accounts max, invite-only. This assumption removes a
  huge amount of complexity (billing, org models, abuse handling) and is revisited in the
  roadmap's "shared assistant mode".

## Assumptions made explicit

| Assumption | Decision | Why |
|---|---|---|
| Deployment | Vercel + Supabase (user-confirmed) | Accessible anywhere, zero home infra |
| Default AI | Gemini API free tier (user-confirmed) | $0, strong function calling, 2-min setup |
| Language | English only (user-confirmed) | RTL/Hebrew deferred |
| Source of calendar truth | **Google Calendar is the only calendar store** | No sync-conflict class of bugs; we cache reads, never fork writes |
| Nutrition accuracy | LLM estimation, ±20% acceptable | No food-database API dependency; good enough for trends |
| Sleep data | Derived (no wearable yet) | Recommendations from calendar + workload; wearables are a roadmap item |
| Reminders channel | In-app + daily plan surface | Push/email in roadmap; Vercel cron drives the morning plan |

## What "not a chatbot" means concretely

1. Every NL input resolves to **typed actions** (create_task, log_meal, …) executed against real
   tables — never just a text reply.
2. The UI leads with **views of state** (Today, Tasks, Fitness…), not a message thread. The
   command bar (⌘K) is an overlay, dismissed after use.
3. The system speaks first: the daily plan is generated by cron before she wakes up.
4. Memory is retrieval-based: relevant facts are injected per request, never the whole store.

## Requirements the original brief was missing (added)

- **Idempotency / undo**: every assistant action returns a receipt chip in the UI with one-click
  undo (delete the created row / restore the event). NL is ambiguous; cheap reversal beats
  confirmation dialogs.
- **Timezone handling**: a per-user timezone setting; all planning math runs in it. Cron fires in
  UTC and converts.
- **Quota resilience**: Gemini free tier has rate limits; the provider layer retries with backoff
  and the app degrades gracefully (logging still works; only AI parsing pauses).
- **Data export**: her data, her file — JSON export from Settings. A personal product must not be
  a data trap.
- **Trust boundary**: the assistant never emails, spends, or messages anyone. Action surface is
  limited to the app's own tables + Google Calendar.

## Success criteria

- Any of the six example commands ("Schedule dentist Thursday at 3", "I ate chicken and rice", …)
  round-trips to a correct DB/calendar mutation in one message.
- Morning plan waiting in the Today view by 6:30 AM local, every day.
- Zero monthly cost at expected usage (~100 assistant calls/day fits Gemini free tier).
- Setup from clone to running: < 5 minutes after Supabase/Google credentials exist.
